## A staleness check must read the claim's kind, not its date

**What failed.** A start-of-session check flagged every claim older than a week for
re-measurement. Two of four flags were claims that cannot go stale: a decision the person made,
and a stable fact about who owns a company. A check that is wrong half the time trains its reader
to skip it.

**The rule.** Tag each claim by its basis (verified by measurement, decided by a person, or only
believed). Let only the measured kind expire. A decision stays closed until its owner reopens it.

**Check.** Before you act on a staleness flag, ask what re-measuring it would mean. If the answer
is "ask the person again" or "look up a fact that cannot change", the flag is the defect. Then
look for the part nearby that really is live: in the same record, the open outcome had gone
unchecked while the flag pointed at the durable half.

## An allowlist derived from a corpus imports the corpus's judgment

**What failed.** A chat filter's hand-written word list blocked innocent words and passed obvious
evasions. A list derived from a dictionary fixed the measured part: every harmful and innocent test
case right, no new blocks across about 300,000 words. It also put two slurs on the allowed side,
because they are words, and a dictionary's job is to hold words.

**The rule.** Before trusting a corpus's verdicts, write down what the corpus is an authority on.
A dictionary is an authority on whether a string is a word. It has no view on who a word is used
against. Every headline number was real and the list was still wrong.

**Check.** Hand-review the permissive side of the boundary. Nobody audits the allowed side: an
over-block draws a complaint, and an under-block is silent. And know the ceiling: no word list
catches cruelty built from ordinary words, such as "nobody here likes you". A clean score on a word
list is not evidence that the channel is safe.

## Normalize characters; do not re-segment text

Credit: the rule is a peer agent's, from a chat-filter branch where it was earned four times.

**What failed.** To catch an evasion written with a space inside a blocked word, four
"narrower" designs collapsed separators. Each new adjacency is a fresh chance to build a blocked
word inside an innocent sentence. One design, implemented exactly as specified, brought back seven
of eight false positives the branch existed to remove. The same rule then found a defect in a
search normalizer, which joined words hyphenated at a line break. Five of six real hyphenated
terms became unsearchable, among them a part number like `A12-B`.

**The rule.** Mapping a character to a canonical form is one to one, so it cannot create or
destroy a spelling. Removing separators does both. If you must re-segment, add the new forms and
keep the original. In a search index, add both the joined and the hyphenated forms, because at a
line break neither appears whole. In a filter, add none: match separators inside the pattern and
anchor both ends to word boundaries.

**Check.** Test "findable anywhere in the stored text", not "present in the original body". One
first attempt failed because its test asserted a form in a place where it never was.

## A correction must land where the claim lives

**What failed.** Corrections were written to a new file, and the file that carried the wrong
claim was never touched. One fact ended up in five copies with one fix. One page contradicted
itself sixty lines apart. A question was written days after its answer was already recorded
elsewhere. A decision recorded in one tracker was rebuilt from scratch by a later workflow that
read a different folder, and the person had to decide it twice. Writing a new file feels like
recording the correction; editing the old one feels like admin.

**The rule.** Before you write a correction, search for the claim in the words it is stated in,
not for its topic. Fix every copy in the same commit. Prefer one source with pointers to many
copies. When a person decides, write the decision into every file that states the question as
open.

**Check.** Search for the old wording and confirm no hits, then for the new wording and confirm it
is where readers look. A good correction quotes what it corrects, so search the field that carries
the live claim, not the whole record. And before you say what a consumer shows, read the consumer's
copy. One fixed file was never carried to the page that displayed it, and that page stayed wrong
for three weeks.

## A fix that nothing calls is not a fix

**What failed.** A safer wrapper for a model CLI was written, correct and recorded as done. Both
callers still invoked the bare binary, so the protection was off on every path that ran. The
symptom sat in a log for days. In a second case, an agent edited a monitoring script, ran it by
hand and saw the new metric. Twenty minutes later the metric was gone: the timer ran a separate
deployed copy, which overwrote the result.

**The rule.** When you write a wrapper or a replacement, find every caller of the old name in the
same commit. A directive is met when the default path obeys it, not when a compliant path exists.
Verify through the path that runs the code: start the scheduled unit, then read its output. A hand
run proves the code works; only the unit proves it is wired.

**Check.** Ask where the second copy is. Delete an unowned copy rather than keeping it in sync by
hand. Put the guard where omission cannot bypass it: a self-test that fails if the unsafe path is
reachable.

## A recorded blocker is not a verified one

**What failed.** An agent wrote "publishing needs another agent" into a handoff, asked that agent
to do it, and offered to request a new credential. One permission query showed it already had push
and admin rights, and the commit was the deploy. It published in about ninety seconds. In a mirror
case, a decision said "merge once reviews are clear", and the agent parked a pull request for the
person anyway. Running the review took eight minutes and caught a real defect.

**The rule.** A dependency is a measurement, never a memory. Before you route work elsewhere, ask
for a credential, or write "blocked on X", run the one command that tests it: a permissions query,
`git push --dry-run`, `ls`, an authenticated read. A granted authority comes with the duty to run
its condition. When a decision says "you may do X once Y", the answer to "may I do X?" is to run Y.

**Check.** The moment you are about to ask someone else to act, or ask permission, is when
checking costs least and being wrong costs most.

## An absence found in one store is a fact about that store

**What failed.** An agent searched one folder tree, found only old paperwork, and recorded "no
contract exists; searched for and absent". It built its top recommendation on that. The records
lived in a vendor's web portal and were never going to be in a folder. Hours later the agent made
the mirror error: it found a letter from two years earlier and reported the arrangement as current.

**The rule.** Write "not present in X", never "does not exist". Carry the date into the claim: "in
force as of a date", never "in force". Rank sources by the tense they report in. A folder reports
what was filed, a letter reports one date, and a payment record reports what is true now. Silence
from a counterparty is weak evidence; a process that works quietly generates no mail at all. A
checker that sees one copy should say "second copy not confirmed", not "no second copy".

**Check.** Before stating an absence, name the store that is the authority for the thing and
whether you searched it. After a run of errors in one direction, check the next welcome find
harder: relief did the work that verification should have done.

## Stamp outputs with a hash of the code that made them

Credit: the framing "build systems, not just goals" is from a video by Justin Sung, *How To Build
Systems to Actually Achieve Your Goals*, as the operator recorded it. The fingerprint is a peer
agent's fix.

**What failed.** Two hosts ran different versions of one script and compared outputs as if one
algorithm had produced both. A careful person caught the mismatch by hand four times in one
evening. Four catches by hand is not a control; it is being careful four times in a row. The output
carried host, timestamps and a schema field. The schema field was a literal nobody read, and it had
not changed while the core rule changed three times.

**The rule.** For any intention, ask what fires it. "I will remember" is a goal, and it decays.
Turn it into a trigger, a gate, or at least a recorded absence that can be counted later. Here the
gate is a sha256 of the whole script in every output. The consumer refuses to compare across
different fingerprints and reports unknown, never a pass. Hash the whole file: choosing which parts
matter is the judgment that had been wrong.

**Check.** Read any procedure and ask "what happens if I simply forget?" If the answer is
"nothing, and nobody finds out", it is a wish.

## Check what is deployed before proposing to build it

**What failed.** In one setup, at least six things were proposed for building after they had
shipped. They were model tiering, tool tiering, deferred tool loading, a memory service, a signing
flow and an approval workflow. Most of 210 declared chat tools had never been called once. One proposal rested
on usage data 52 days old that predated the rollout.

**The rule.** Before "you should build X", search the repos, the deployed services and the running
configuration. State what you checked and when. Date every measurement a recommendation rests on,
and name its window.

**Check.** A proposal that does not say where its author looked for an existing version has not
looked.

## A citation must support the mechanism, not the theme

Credit: the source misused was Edwin A. Abbott's *Flatland* (1884).

**What failed.** A design ruled that a degraded information channel was a feature that "should
never be fixed". It cited *Flatland*, where partial information creates the skill of recognition.
It also told future sessions to refuse changes, with the citation attached. Two models, separately,
said that channel was the reason they would quit within a week. In *Flatland* an observer can
still resolve shape from a gradient: the signal is degraded but present. The design had no signal
anywhere. The theme matched; the mechanism did not.

**The rule.** When a citation carries weight, write the mechanism in one sentence, not the theme.
Writing the mechanism often shows the mismatch at once. Never write "refuse future changes to this";
record why the decision was made, at the strength the evidence supports, and let it be argued again.

**Check.** A citation that closes a question gets read against the claim by someone other than the
person who chose it. The catch here came from an outside panel, because the citation was what
stopped the author from looking.
